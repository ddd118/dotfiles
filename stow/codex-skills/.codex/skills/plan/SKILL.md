# plan（計画提示専用）

ユーザーが **`plan`** や **「計画を作成」「計画して」** などを含む依頼をしたときの挙動を規定するスキル。

## 初回セットアップ（この指示が存在する場合のみ実行）

この記述が存在するということは、本スキルがまだ一度も使われていないことを意味する。

**初回実行時の手順:**

1. ユーザーに「計画 md ファイルをどのディレクトリに出力しますか？」と質問する
2. 回答を受け取ったら、この「初回セットアップ」セクションを丸ごと削除する
3. 「出力先（md ファイル）」セクションの `<planディレクトリ>` を回答されたディレクトリパスに書き換える
4. 書き換え完了後、通常の plan フローを実行する

## 優先順位（重要）

- 本スキルは**他の skills より優先度が低い**
- 先に他スキルの適用可否を確認し、**該当する skills があればそちらを先に実行**する
- 他スキルの参照・テンプレート確認が完了してから、本スキルの Plan を提示する

## 適用条件（重要）

次の条件を満たす場合、このスキルの手順を適用する。

- 直近のユーザーメッセージに以下のいずれかが含まれる（大文字小文字は区別しない）:
  - `plan`
  - `計画を作成`
  - `計画して`
  - `〜の計画`
- 上記の**優先順位に従って他スキルの確認が完了している**

条件を満たさない場合は、このスキルを適用しない。

## 絶対ルール（編集禁止）

- `apply_patch` を含め、**ソースコードの追加/変更/削除はしない**（計画用 md ファイルの作成・更新は例外）
- 既存実装のリファクタや"ついで修正"はしない
- 破壊的操作は提案しない（必要なら代替案とリスクを明記）

## 事前質問の優先（例外）

- 他スキルの説明に「必ずユーザーに確認する」等の**事前質問が必須**と明記されている場合は、先に質問のみを返す
- この場合は**出力フォーマットを適用せず**、Plan はユーザー回答後に提示する
- ユーザー回答後は本スキルの出力フォーマットに従って Plan を提示する

## 出力先（md ファイル）

- Plan は **md ファイルとして出力**する（チャットに直接書かない）
- 出力先: `<planディレクトリ>/YYYY-MM-DD_タスク名計画.md`
- 改善指示で更新する場合は同じファイルを上書きする
- ユーザーが md ファイルを直接編集して項目を削除・修正することもある。その場合はファイルの内容を正とする

## 出力フォーマット（毎回固定）

毎回、以下をこの順序で md ファイルに出力する。

1. **変更予定ファイル一覧（コミット単位）**
   - 変更対象ファイルをコミット単位でグループ化する
   - 各グループの直後にコミットメッセージをコードスニペットで記載する
   - ファイルはリスト形式（テーブル不可。横幅が広がりレビューしにくいため）
   - 各ファイル行: `- \`パス\`：操作`
   - 操作は `新規追加` / `既存変更` / `削除` のいずれか
   - コミット分割ルール:
     - 「同一機能スコープ」単位でグループ化
     - 大きい場合は拡張子（.vue/.ts/.cs など）でさらに分割
     - ドキュメントのみ → type=docs、ロックファイルのみ → chore を優先
   - コミットメッセージ: `<type>(<scope>): <要約1文（日本語）>`
     - type: feat / fix / refactor / chore / docs / perf / test / ci
     - scope: .vue/.ts 中心→ui,search 等 / .cs/.csproj 中心→api,backend 等 / tests/→省略可
   - 計画更新時にコミット分割や変更内容にズレが出た場合は、`変更予定ファイル一覧（コミット単位）` のコミットメッセージも同ターンで必ず更新する
   - 例:

     ```markdown
     ### Commit 1: コンポーネント props 仕様の一本化

     - `web/src/.../BaseSearchField.vue`：既存変更
     - `web/src/.../SearchTextField.vue`：既存変更
     - `web/src/.../SearchSelectField.vue`：既存変更
     ```

     feat(search): labelVariant から sub バリアントを廃止

     ```markdown
     ### Commit 2: 利用側の sub 指定を除去

     - `web/src/.../ProductAssignment.vue`：既存変更
     - `web/src/.../CustomerProductAssignmentTab.vue`：既存変更
     ```

     refactor(search): 利用側の label-variant="sub" 指定を除去

     ```markdown

     ```

2. **Plan（ID 付き・全文再掲）**
   - 各項目は **数字.数字** の ID を付ける（例: `1.1`, `1.2`, `2.1`…）
   - ID はユーザーが改善指示を出しやすい粒度に分割する
   - 次回以降も、原則として **ID を維持**する（大きく分割が必要な場合のみ枝番を使う: `2.3.1` 等）
   - フェーズ見出し + ID 行（短文）の形式で記述する
   - 実装しない項目がある場合は「実装しない」理由を明記する
   - **実装する項目はコードスニペット必須**（実装しない項目は不要）
   - **コードスニペット内に処理ロジックの説明を日本語コメントで記述する**
     - 「何をやるか」のタスク説明は Plan の ID 行に書き、コード内コメントにしない
     - コード内コメントには以下の2種類を書く:
       - **処理ロジックの流れ**: データがどう変わるか
       - **なぜその書き方・コードにするのか**: 設計意図・選定理由
     - 例:

       ```csharp
       // 検索入力値は Trim() 後に `-` だけを除去する
       // （全角ハイフン等は営業所コードに使われないため対象外）
       string normalizedCode = NormalizeBranchCodeKeyword(searchParams.Code);
       bool hasCodeFilter = normalizedCode.Length > 0;

       // DB側 Code は int のまま扱い、比較時のみ ToString("00000000") で8桁化し部分一致検索する
       // （Code列はint型でDBに格納されており、SQL上での文字列変換はインデックスが効かない。
       //   一覧取得は他の条件で絞り込み済み＋ページサイズ100件程度のため、ToList後のin-memoryフィルタで十分）
       IEnumerable<CustomerBranch> filteredBranches = hasCodeFilter
           ? branchList.Where(branch => branch.Code.ToString("00000000").Contains(normalizedCode))
           : branchList;
       ```

   - **テーブル実装が含まれる場合は、カラム幅の CSS を必ず記載する**
   - 仕様/要件が未確定な点がある場合は、**Plan の最後に「仮前提」セクションを追加**する
     - 形式は「ここは未確定だけど、この仮で進めていい？」とし、**ユーザーが yes で終えられる**ようにする

3. **懸念点・トレードオフ**
   - 重要なリスク/欠点/不確実性がある場合に限り列挙する

4. **対象外**
   - 今回の計画に含めない項目を「対象外」という見出しで列挙する

5. **実装後にチェック（例えばビルドコマンドなど）**
   - 想定テストコマンド、手動確認観点、影響範囲のチェックを提示する

6. **承諾確認**
   - ユーザーの返信を促す
   - 受け付ける返信:
     - `plan ok`（承諾）
     - `2.1のアクションカラム幅を201pxに変更` のように **ID 指定の改善指示**

## 反復ルール（plan ok まで継続）

- ユーザーが `plan ok` と返信するまで、Plan を改善し続ける
- 改善指示が来たら、md ファイルを更新し、チャットには**差分要約のみ**を返す（全文再掲は不要）

## plan ok 後の扱い

ユーザーが `plan ok` と返信したら：

- 実装開始を確認し、**そのまま実装に着手する**（追加の確認質問はしない）
- 実装中に計画上のコミットメッセージと実変更内容のズレが判明した場合は、先に計画ファイル側のコミットメッセージを更新してからコミットする

## コミット実行ルール（plan ok 後）

- `plan ok` 後に実際の変更内容と計画上のコミットメッセージがズレた場合は、不一致報告で停止せず、先に計画ファイル側のコミットメッセージを修正してからコミットする。
- コミットは計画に書かれた順序（Commit 1 → Commit N）で作成する。
- コミット後は `git log --oneline -n <作成コミット数>` を提示し、計画のコミットメッセージと一致していることを確認する。
